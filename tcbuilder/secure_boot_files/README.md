# Support files for the secboot commands

Signing helper scripts and templates used by `torizoncore-builder secboot`, plus one key.

## `ti-degenerate-key.pem`

The *degenerate* signing key for K3 SoCs that `secboot sign-bootloader-k3` uses by default. It is
not secret: the certificates it produces carry no security property. It exists because the boot ROM
of GP silicon expects a signed container while verifying nothing.

This file is the degenerate key of Toradex's engineering K3 key set, generated by Toradex on
2024-11-22 with `openssl genrsa -F4 -out ti-degenerate-key.pem 4096`: RSA 4096-bit, PKCS#8 PEM,
sha256 `ba232085efab23c6a926879dbfdbc1e7054894eff50f19ae60cbd5c38264a976`. Toradex's AM62 images
are built with it, so re-signing one of them with the default reproduces its GP artifacts byte for
byte, provided the image was built with reproducible certificates
(`TDX_K3_SECBOOT_REPRODUCIBLE = "1"` in meta-toradex-security). Like the rest of TorizonCore
Builder, it is licensed under the GPLv3.

It is not TI's degenerate key. TI publishes a different one (RSA 1024-bit) in `core-secdev-k3` and
in U-Boot's `arch/arm/mach-k3/keys/`, and a build that follows the Toradex secure-boot documentation
generates its own. To reproduce the GP artifacts of an image built with either, pass that key with
`--k3-degenerate-key`, again given reproducible certificates. The device boots the same either way.

The file keeps the name a K3 key directory expects, so it can be copied as is into the
`TDX_K3_SECBOOT_KEY_DIR` of a Yocto build that should sign its GP artifacts with the same key.

`secboot sign-bootloader-k3` stages it into every signing root, because the K3 binman descriptors
declare a `ti-degenerate-key` image whose file must exist, whatever the SoC. What it signs depends
on the SoC:

- AM62 (`verdin-am62`): the two artifacts a Torizon OS build also signs with its degenerate key,
  `tiboot3-am62x-gp-verdin.bin` and the `tifsstub-gp` subimage inside `tispl.bin`.
- AM62P (`verdin-am62p`): nothing. TI ships no GP firmware for this SoC, so there is no GP container
  and no `tifsstub-gp`.

Everything else is signed with the customer key passed to `--k3-key`.

Do not add customer or test signing keys to this directory. Test key material belongs under
`tests/integration/samples/signing_keys`.
